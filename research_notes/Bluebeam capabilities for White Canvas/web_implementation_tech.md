## 1. Vector PDF underlay at arbitrary zoom (pdf.js strategies, PDFium/MuPDF alternatives, commercial SDKs)

### Takeaway
Stay on pdf.js 6.5: it now ships exactly the pieces a deep-zoom underlay needs (a "detail canvas" partial renderer, per-operation bounding-box tracking with an `operationsFilter`, and an optional OffscreenCanvas **renderer worker**), needs no `unsafe-eval`, and is Apache-2.0. The only permissively licensed step up is PDFium-WASM (EmbedPDF, MIT/Apache-2.0 — which since Sept 2026 also has an open measurement/calibration plugin); MuPDF.js is AGPL, and commercial SDKs start at about US$1,500 (Apryse) or US$595/month (PDF.js Express Plus) with most prices quote-only.

### Inferences
- Recommended architecture: keep pdf.js; do **not** use its `PDFViewer`. Per PDF board item, keep (a) a low-res whole-page bitmap (always visible, CSS-scaled by the world transform) and (b) a pool of fixed-size tiles (e.g. 1024 px) rendered at `zoom × devicePixelRatio` only for the intersection of the page with the screen, keyed by `(page, zoomBucket, tx, ty)` in an LRU. Each tile is one `page.render({ canvas, viewport: page.getViewport({ scale, offsetX: -tx, offsetY: -ty }), annotationMode: AnnotationMode.DISABLE })`. This is the same idea as pdf.js's own detail canvas, generalised to tiles so panning does not re-render everything.
- For dense CAD sheets the expensive part is replaying the whole operator list per tile. pdf.js 6.5's `recordOperations` (first full render records per-op bounding boxes) + `operationsFilter` (skip ops whose bbox misses the tile) is the built-in answer; the exact shape of the recorded data is internal (`canvas_dependency_tracker`), so wrap it and pin the pdf.js version.
- Setting `GlobalWorkerOptions.rendererSrc` to a self-hosted `pdf.renderer.mjs` moves canvas drawing off the main thread (OffscreenCanvas) and `partialFrames` gives progressive paint. Because the app's CSP already allows `worker-src 'self' blob:` and pdf.js has no eval, no CSP change is expected; needs a device test (Safari in particular).
- Budget per canvas on iOS: stay ≤ 4096×4096 (16.7 MP) per canvas and keep the *sum* of live canvases small — each 4096² RGBA canvas is 64 MB; pdf.js itself drops to 5.2 MP on mobile. Release tiles by setting `width = height = 0` before dropping references.
- Convert finished tiles to `ImageBitmap` (`transferToImageBitmap`/`createImageBitmap`) and draw them with one compositing canvas or as `<img>`/`<canvas>` DOM items inside the transformed world layer; avoid scaling the world layer's canvas with CSS beyond ~2× before swapping in sharper tiles.
- Persist nothing rendered in IndexedDB except perhaps the low-res page thumbnail; vector re-render is cheaper than storing megapixel tiles and keeps offline storage for the source PDFs.
- PDFium-WASM is worth adding only if profiling shows pdf.js too slow or unfaithful on specific CAD output; EmbedPDF's engine can be used headlessly (render region to bitmap in a worker) without adopting its UI. Cost: ~4.7 MB extra WASM.

### Gaps
- No published benchmark found comparing pdf.js 6.x (with renderer worker/partial rendering) against PDFium-WASM or MuPDF-WASM on 100k+ path CAD sheets; needs an in-house test with real drawings.
- Browser support matrix and stability of pdf.js's renderer worker / `enableWebGPU` are not documented in the typings; not verified on iOS Safari.
- Artifex (MuPDF), Nutrient, ComPDFKit and Foxit publish no list prices; Apryse's US$1,500 is an entry figure without a stated unit.
- Foxit Web SDK measurement capabilities: no web-specific developer documentation surfaced.
- Current iOS/iPadOS canvas limits for 2026 OS versions were not confirmed from a primary WebKit source.

## 2. Snap-to-content: extracting vector geometry and indexing it

### Takeaway
pdf.js 6.5 already hands back every path as a compact `Float32Array` of draw-ops with a precomputed bounding box via `getOperatorList()`, so snap geometry can be harvested in a worker without a second PDF engine; index segment boxes in Flatbush (1 M boxes in ~109 ms) and compute intersections lazily around the cursor. PDFium (MIT) and MuPDF (AGPL) offer cleaner object-level/device-level APIs if pdf.js internals prove too brittle.

### Inferences
- Pipeline (all in a Web Worker): `getOperatorList()` → walk `fnArray`, maintain a CTM stack → for each `constructPath` whose paint op strokes/fills, transform points into page space, flatten Béziers adaptively (or keep arcs as arcs when 4-curve circle patterns are detected), and append segments to one `Float32Array [x1,y1,x2,y2]` plus a parallel `Uint32Array` of style/layer ids → `new Flatbush(n, 16, Float32Array)` over segment boxes → `postMessage` with transferables. Persist the typed arrays in IndexedDB keyed by the PDF hash + page so it is computed once and works offline.
- Query: `index.search(cx−r, cy−r, cx+r, cy+r)` with r ≈ 8–12 screen px converted to page units; rank candidates endpoint > intersection > midpoint > perpendicular/nearest-on-segment. Compute intersections **only** among the ≤ few dozen segments returned for the cursor neighbourhood — precomputing all pairwise intersections on a 100k+ segment sheet is O(n log n + k) and k can be in the millions on hatched drawings.
- Cost estimate (scaled from Flatbush's published 1 M ≈ 109 ms): 100k–500k segments index in roughly 10–60 ms; storage is 16 bytes/segment for coordinates plus ~20 bytes/segment for the index, i.e. ~4 MB per 100k segments if Float32 is used. The dominant cost is `getOperatorList()` itself on very dense pages, which is why it should run once in a worker and be cached.
- Hygiene filters materially improve snapping on CAD output: drop zero-length and sub-0.1 pt segments, dedupe coincident segments (CAD exporters often double-stroke), exclude clip paths and white-filled masks, optionally exclude text-as-outlines and dense hatch regions (high segment density with uniform angle), and respect Optional Content (layers) visibility via `getOptionalContentConfig()`.
- Risk: the `constructPath` argument layout and `DrawOPS` codes are internal and have changed across pdf.js majors; pin `pdfjs-dist` exactly and add a unit test that parses a fixture PDF. If this becomes a maintenance burden, the PDFium page-object API is a stable public C API.
- Scanned (raster-only) sheets have no vectors; fall back to raster corner/edge detection on the rendered tile around the cursor (Harris/LSD-style) or disable snapping.

### Gaps
- No official pdf.js documentation describes the 6.x `constructPath` payload; the description above is from reading the shipped bundle, not from a spec.
- No measured numbers for `getOperatorList()` time/memory on real 100k–1M-segment construction sheets.
- Whether pdf.js's `recordOperations` output can be reused to get per-path bounding boxes without re-walking the list was not verified.

## 3. Scale calibration and measurement maths; the ISO 32000 Measure dictionary; polygon booleans

### Takeaway
PDF space is 1/72 inch × `UserUnit`; a calibrated scale is just a metres-per-point factor per viewport, and ISO 32000-1 §12.9 defines exactly how to persist it (page `/VP` viewports → `/Measure` `/RL` dictionary with `/R`, `/X`, `/D`, `/A` number-format arrays; the same `/Measure` goes on Line, PolyLine and Polygon annotations). For area maths use the shoelace formula with holes subtracted, and for robust booleans prefer `clipper2-ts` (pure TS, BSL-1.0) or `polyclip-ts` (MIT) — `clipper2-wasm` needs `unsafe-eval` and is blocked by the app's CSP.

### Cited Findings
**Units and scale in the PDF spec (ISO 32000-1:2008, Adobe-hosted copy)**
- `UserUnit` (page dictionary, PDF 1.6): "A positive number that shall give the size of default user space units, in multiples of 1⁄72 inch… Default value: 1.0" [Inspected] — [PDF 32000-1 Table 30](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)
- pdf.js exposes it as `page.userUnit`, alongside `page.view` and `page.rotate` [Inspected] — [api.d.ts](https://cdn.jsdelivr.net/npm/pdfjs-dist@6.5.438/types/src/display/api.d.ts)

### Inferences
- Core maths (store everything in PDF points, convert at display time): `metresPerPoint = (0.0254 / 72) × UserUnit × scaleDenominator` for a ratio scale (1:100 → 0.035278 m/pt); calibration from two picked points: `metresPerPoint = knownLength / hypot(Δx, Δy)`. Length = Σ segment lengths × k; area = |shoelace| × k² (independent X/Y scales: scale coordinates first, then apply shoelace). Polygon with holes: outer area − Σ hole areas (or sum signed areas with consistent winding). Arc length = r·θ; a circular segment's area = r²(θ − sin θ)/2 for "arc" sides in polylength/area tools. Volume = area × depth; wall area = polylength × height.
- A Measure dictionary that Acrobat-class readers should understand for a metric 1:100 sheet (constructed from Table 262/263, not copied from a product): `<< /Type /Measure /Subtype /RL /R (1 mm = 100 mm) /X [<< /Type /NumberFormat /U (m) /C 0.0352778 /D 100 >>] /D [<< /Type /NumberFormat /U (m) /C 1 /D 100 >>] /A [<< /Type /NumberFormat /U (sq m) /C 1 /D 100 >>] >>`. Imperial: chain `ft` then `in` with `/C 12 /F /F /D 16` on the inches element. Multiply `X[0].C` by `UserUnit` when it is not 1.
- Interop practice: write the scale twice — a page `/VP` entry (so other tools' *new* measurements inherit it) and `/Measure` on each measurement annotation (so the *existing* value is reproducible) — and also put the human-readable result in `/Contents` and draw it in the appearance stream, because not every reader recomputes from `/Measure`.
- Multiple scales per sheet (details at 1:5 beside a 1:100 plan) map naturally to the app's data model as "viewport" items: `{ bbox in page pts, metresPerPoint, unit, precision, label }`, resolved last-wins with the *first point* rule, mirroring the spec so export is lossless.
- Library choice: `clipper2-ts` for cut-outs, unions of takeoff regions and offsetting (it works on scaled integers, which is what makes Clipper robust — multiply PDF points by e.g. 1000 before clipping). `polyclip-ts` is the maintained successor line of `polygon-clipping` for float GeoJSON-style input. Boost Software License 1.0 is a permissive licence without a binary attribution requirement, so it is closed-source friendly.
- Do units yourself with a small table (mm, cm, m, in, ft, ft-in fractional, yd; m², ft², yd²; m³, yd³) rather than pulling `mathjs`; the unit libraries found are either stale or large.

### Gaps
- Not verified in this research: exactly which `/Measure` and `/VP` details Bluebeam Revu and Acrobat read or write in practice (out of scope here; owned by other researchers) — the dictionary above follows the standard but should be round-trip tested.
- ISO 32000-2 (PDF 2.0) changes to measurement (e.g. geospatial `/GEO`, point-data) were not checked; the cited text is ISO 32000-1.
- No head-to-head robustness/performance benchmark between `clipper2-ts`, `polyclip-ts` and `martinez` was found for 2026 versions.

## 4. Flood-fill region detection ("dynamic fill")

### Takeaway
Two workable routes, best combined: (a) a raster flood fill on a rendered tile followed by contour tracing and simplification — simple and tolerant of messy drawings; (b) planar-face finding on the extracted vector segments — exact corners, but needs gap closing. The licence trap is the vectorisers: Potrace ports are GPL-2.0 and `marching-squares` is AGPL-3.0; and OpenCV.js cannot run under the app's current CSP because its embind glue uses `new Function`.

### Cited Findings
- Two open takeoff tools publish how they do it: pdf2takeoff's "Magic Fill" is "flood fill plus boundary trace to read a room's area from its walls", closing doorway gaps "using scale, text labels, vector geometry or door width" [Vendor/Docs] — [pdf2takeoff](https://github.com/ajflow/pdf2takeoff)
- OpenTakeoff's one-click area: "a flood fill bounded by the drawing's linework traces the polygon. Vertices snap to corners. Hatch and pattern linework are classified separately so they don't count as walls"; raster fallback for scans uses "adaptive thresholding, polarity detection for blueprint negatives, and gap bridging"; the feature is currently gated off by default and the project notes browser and MCP room detection "can produce different boundaries" [Vendor/Docs] — [opentakeoff fork](https://github.com/kleenkanteen/opentakeoff)
- OpenCV.js default build whitelist (4.x branch config) includes `floodFill`, `findContours`, `approxPolyDP`, `connectedComponentsWithStats`, `morphologyEx`, `distanceTransform`, `Canny`, `HoughLinesP` — [opencv_js.config.py](https://raw.githubusercontent.com/opencv/opencv/4.x/platforms/js/opencv_js.config.py)
- `@techstark/opencv-js` 5.0.0-release.1 (Apache-2.0, published 2026-06-24) repackages `https://docs.opencv.org/5.0.0/opencv.js`; the single `dist/opencv.js` is 13 MB and contains two `new Function(` call sites in its embind glue (`craftInvokerFunction`), which need `script-src 'unsafe-eval'` [Inspected] — [README](https://cdn.jsdelivr.net/npm/@techstark/opencv-js@5.0.0-release.1/README.md); [opencv.js](https://cdn.jsdelivr.net/npm/@techstark/opencv-js@5.0.0-release.1/dist/opencv.js)
- `q-floodfill` 1.3.1 — MIT, last published 2020-09-27 (small ImageData flood fill) [Registry] — [npm](https://www.npmjs.com/package/q-floodfill)
- **Licence flags:** `potrace` (npm 2.1.8) is GPL-2.0; `esm-potrace-wasm` 0.5.1 is "GPL-v2.0, due to the original Potrace license"; `marching-squares` 1.0.0 is AGPL-3.0 [Registry/Inspected] — [npm potrace](https://www.npmjs.com/package/potrace); [esm-potrace-wasm README](https://cdn.jsdelivr.net/npm/esm-potrace-wasm@0.5.1/README.md); [marching-squares README](https://cdn.jsdelivr.net/npm/marching-squares@1.0.0/README.md)
- Permissive tracing options: `imagetracerjs` 1.2.6 (Unlicense, last published 2020, 5.5 KB gzip); `d3-contour` 4.0.3 (ISC, published 2026-11-03, 3.5 KB gzip); `@thi.ng/geom-isoline` 2.1.233 (Apache-2.0); `vectortracer` 0.1.2 (MIT, 2023); `simplify-js` 1.2.4 (BSD-2-Clause) for Douglas-Peucker simplification [Registry] — [npm imagetracerjs](https://www.npmjs.com/package/imagetracerjs); [Bundlephobia d3-contour](https://bundlephobia.com/package/d3-contour@4.0.3); [npm @thi.ng/geom-isoline](https://www.npmjs.com/package/@thi.ng/geom-isoline); [npm vectortracer](https://www.npmjs.com/package/vectortracer); [npm simplify-js](https://www.npmjs.com/package/simplify-js)
- Vector route building blocks: `@turf/polygonize` 7.4.0 (MIT, published 2026-08-03, 5.1 KB gzip) and `planar-face-discovery` 2.0.7 (licence **CC-BY-4.0**, last published 2021-11-14) [Registry] — [npm @turf/polygonize](https://www.npmjs.com/package/@turf/polygonize); [Bundlephobia](https://bundlephobia.com/package/@turf/polygonize@7.4.0); [npm planar-face-discovery](https://www.npmjs.com/package/planar-face-discovery)

### Inferences
- Raster route (recommended first implementation, pure TypeScript in a worker, no OpenCV): render a tile around the click at a fixed resolution (e.g. so that 1 px ≈ 5–10 mm real, capped ~2–3k px per side) with annotations off → binarise (luminance threshold; treat coloured hatch as "not wall" by a stroke-colour/width rule) → **gap tolerance** by morphological closing/dilating the wall mask by g px where g = (door width, ~0.9 m) × scale ÷ 2 → scanline flood fill from the seed → erode back by g → trace the outer boundary and holes (Moore-neighbour or marching squares via `d3-contour`) → Douglas-Peucker simplify → snap vertices to the nearest vector endpoints/intersections from the Q2 index → convert to page points. If the fill touches the tile border, enlarge the tile and retry; if it exceeds a sanity area, report "region not closed".
- Vector route: take segments in a neighbourhood, extend/snap endpoints within tolerance, split at intersections (noding), build a half-edge planar graph, enumerate faces, pick the face containing the click (`@turf/polygonize` implements the polygonize step). Exact, but open door swings, double-line walls, hatches and text make it fragile; it works best as a refinement (snap the raster contour to vector corners), which is what the OpenTakeoff description amounts to.
- Islands (columns, shafts) fall out naturally as holes of the filled component; expose "include/exclude islands".
- If OpenCV is really wanted, three CSP-compliant options: (1) custom Emscripten build with `-sDYNAMIC_EXECUTION=0` (removes `new Function`) and only the needed modules; (2) load it in a dedicated worker script whose HTTP response carries its own relaxed CSP header (a per-path `headers` rule in `vercel.json`) — workers loaded from a network URL are governed by the CSP delivered with the worker script, but this must be tested in each browser; (3) a sandboxed iframe. Option 1 is the cleanest.
- `planar-face-discovery`'s CC-BY-4.0 is a content licence rarely used for code; legal review before bundling. `imagetracerjs` is unmaintained since 2020 but public-domain and tiny; fine to vendor.

### Gaps
- No engineering write-up from commercial takeoff vendors (Togal.AI, Kreo, STACK) describing their region-detection algorithms was located; the only concrete public descriptions found are the two open-source projects above (self-described, untested).
- No published accuracy figures for raster flood-fill room detection on real construction sets.
- `@turf/polygonize` behaviour on un-noded, gappy CAD linework was not tested.

## 5. Writing and reading real PDF annotations (pdf-lib and forks, pdf.js, annotpdf, PDFium, MuPDF, XFDF)

### Takeaway
No permissive JS library gives a turnkey "write Bluebeam-grade markups" API: pdf-lib (use the maintained `@cantoo/pdf-lib` fork, MIT, works in Deno) can write any annotation dictionary and appearance stream but only through its low-level object API, so you generate the appearance yourself from the same geometry you draw as SVG. pdf.js reads annotations well (including replies and review state) but its editor only writes FreeText/Highlight/Ink/Stamp/Signature and it does not parse `/Measure` or `/BE`. EmbedPDF's MIT PDFium build is the open engine with native cloud-border, intent, vertices, appearance-generation and flatten calls; MuPDF.js has the same but is AGPL.

### Inferences
- Recommended write path (browser *and* Deno): `@cantoo/pdf-lib` low-level API — build each annotation with `pdfDoc.context.obj({ Type: 'Annot', Subtype: 'Polygon', Rect, Vertices, C, IC, CA, BS, BE: { S: 'C', I: 1 }, IT: 'PolygonCloud', T, Subj, Contents, NM, M, CreationDate, F: 4, Measure: … })`, attach an `/AP /N` form XObject whose content stream is generated from the *same* path data the canvas uses for SVG (moveto/lineto/curveto operators; convert SVG arcs to Béziers), register it and push the ref onto the page's `/Annots`. These low-level calls (`context.obj`, `context.register`, `context.stream`/form XObject creation, `page.node`'s `Annots`) are standard pdf-lib internals but should be verified against the fork's typings before coding — they were not inspected in this research.
- Always write an appearance stream. Viewers differ on whether they synthesise cloud borders, dimension-line leaders or callouts from the dictionary; with an `/AP` present the markup looks identical everywhere while the dictionary keys (`/BE`, `/IT`, `/Measure`, `/LE`, `/CL`) keep it *editable* as a native cloud/dimension/callout in tools that understand them.
- Round-trip metadata mapping for the app's item rows: author → `/T`; subject → `/Subj`; comment → `/Contents` (+ `/RC` rich text); id → `/NM`; created/modified → `/CreationDate`, `/M`; replies → separate `Text` annotations with `/IRT` (and `/RT /R`); status changes → `Text` annotations with `/IRT`, `/State` (e.g. `Accepted`), `/StateModel /Review`, authored by the user who set the status; grouping → `/RT /Group`; layer → Optional Content (`/OC`). Custom fields that have no PDF home can go in a private key on the annotation dictionary (ignored by other readers).
- Read path: `getAnnotations()` from pdf.js gives geometry, author, replies and state for import into board items; to recover `/Measure` and `/BE` open the same bytes with pdf-lib and read the raw dictionaries (cheap — no rendering).
- Flattening = draw each annotation's appearance XObject into the page content (`page.drawPage`-style embed or direct `Do` operator with the annotation's `Rect`→BBox matrix) and remove it from `/Annots`. pdf-lib has no ready-made annotation flatten (inference from its README); PDFium's `EPDFAnnot_Flatten` or MuPDF's `bake` do it natively.
- Incremental save (`forIncrementalUpdate`) in the Cantoo fork is valuable for large sheet sets: append markups without rewriting a 200 MB file and without invalidating existing signatures.
- XFDF export is worth supporting as the lossless interchange with Apryse/Nutrient/Acrobat-class tools; it is a straightforward attribute mapping from the same annotation model. No maintained open-source JS XFDF library was found, so plan a small in-house codec.
- `annotpdf` is useful as readable reference code for appearance streams and cloudy borders but is too stale (2022) to depend on.

### Gaps
- Did not verify the Cantoo fork's low-level API signatures or whether it can parse/modify *existing* annotation appearance streams.
- The full ISO 19444-1 text is paywalled; whether XFDF 3.0 has explicit measure-dictionary elements could not be confirmed (only the table of contents was visible).
- No test was run to confirm how third-party viewers render app-written `/BE` clouds or `/Measure` dimensions; needs a compatibility matrix (Acrobat, Bluebeam, Chrome/Edge PDFium, Preview, pdf.js).
- Whether pdf.js `saveDocument()` preserves unknown annotation keys written by other tools was not tested.

## 6. Drawing comparison / overlay

### Takeaway
The display side is trivial in a browser (tint each revision and composite with `multiply`, or diff pixels with pixelmatch, 2.8 KB); the hard parts are registration and turning pixel noise into reviewable change regions. OpenCV.js has ORB/AKAZE, RANSAC homography/affine and ECC in its default build, but no phase correlation and its stock build is blocked by the app's CSP — for same-origin CAD revisions, vector-anchored or manual 2/3-point alignment plus a small custom diff-clustering pass is more practical.

### Cited Findings
- `pixelmatch` 8.0.0 — ISC, published 2026-10-06, 5.8 KB min / 2.8 KB gzip [Registry] — [npm](https://www.npmjs.com/package/pixelmatch); [Bundlephobia](https://bundlephobia.com/package/pixelmatch@8.0.0)
- OpenCV.js default whitelist (4.x config) **includes** `ORB`, `AKAZE`, `BRISK`, `BFMatcher`, `findHomography`, `estimateAffine2D`, `findTransformECC`, `matchTemplate`, `warpAffine`, `warpPerspective`, `getAffineTransform`, `connectedComponentsWithStats`, `morphologyEx`; **absent**: `SIFT`, `FlannBasedMatcher`, `estimateAffinePartial2D`, `phaseCorrelate` — [opencv_js.config.py](https://raw.githubusercontent.com/opencv/opencv/4.x/platforms/js/opencv_js.config.py)
- The npm OpenCV.js build (13 MB) uses `new Function` in embind → needs `'unsafe-eval'` (see Q4) [Inspected] — [opencv.js](https://cdn.jsdelivr.net/npm/@techstark/opencv-js@5.0.0-release.1/dist/opencv.js)
- Open-source precedent: pdf2takeoff's revision compare is "a colour-blended overlay: red for removed, blue for added, dark ink for unchanged", with "auto fit and nudge alignment" [Vendor/Docs] — [pdf2takeoff](https://github.com/ajflow/pdf2takeoff)
- Commercial SDKs treat comparison as a separate capability (Apryse lists it apart from the Base Package) [Vendor/Docs] — [Apryse pricing](https://apryse.com/pricing/webviewer)

### Inferences
- Overlay rendering: render revision A and B tiles for the same world rectangle; recolour each on its own canvas (`globalCompositeOperation = 'source-in'` with a fill, or a tiny per-pixel pass mapping ink darkness to red/blue alpha), then composite both onto white with `'multiply'` — unchanged ink becomes near-black, removed stays red, added stays blue. `'difference'` gives a quick "anything changed" view. Because both are ordinary tiles this works at any zoom with the Q1 tile pipeline; no full-sheet bitmap is needed.
- Alignment maths: 2 point pairs → similarity transform (uniform scale s = |q2−q1|/|p2−p1|, rotation θ = atan2 difference, translation); 3 non-collinear pairs → exact affine by solving the 6-unknown linear system `[x y 1]·[a c e; b d f] = [x' y']` (invert the 3×3 of source points); 4+ pairs → least-squares affine or homography. Store the result as a 2×3 matrix on the overlay item and apply it as an extra `transform` in `page.render()` so revision B is *re-rasterised* aligned, not resampled.
- Auto-alignment options in order of practicality: (1) same page size + same title block → identity; (2) vector anchors — match title-block/border rectangle corners or grid-bubble centres from the Q2 geometry of both pages and solve a similarity transform; (3) raster features — ORB/AKAZE + `BFMatcher` (Hamming) + `estimateAffine2D` with RANSAC on ~2k-px downsampled renders; refine with `findTransformECC`. Line drawings have many repeated, low-texture features, so always show the user the residual and offer manual 3-point override. Phase correlation (translation only) would need a small FFT implementation because `phaseCorrelate` is not in the default OpenCV.js build.
- Auto-clouding changes: compute a binary change mask at moderate resolution after a 1–2 px tolerance dilation of each sheet (kills anti-alias/registration jitter) → morphological close with a radius of a few mm of paper to merge strokes of one change → connected-component labelling (two-pass union-find in TS is ~50 lines) → drop tiny components → for each cluster take the padded bounding box or convex hull → emit a revision-cloud item (Q8) with status "unreviewed". Cluster count and total changed area give a per-sheet change score for a revision dashboard.
- Vector-level diff is a possible differentiator: hash each path (rounded coordinates + stroke style) from both revisions' operator lists and diff the sets — immune to raster noise and gives exact changed objects; raster diff remains the fallback for scans.

### Gaps
- No public engineering write-up on how commercial tools auto-align or auto-cloud revisions was found.
- No measured accuracy/perf data for ORB/AKAZE registration of architectural line drawings in OpenCV.js.
- The OpenCV whitelist cited is the 4.x branch config; the 5.0 build shipped in `@techstark/opencv-js` was not checked symbol-by-symbol.

## 7. OCR and sheet intelligence (OCR engines, title blocks, hyperlinks, symbol counting, multimodal LLMs, MCP)

### Takeaway
For vector PDFs read text straight from pdf.js; reserve OCR for scans, where tesseract.js 7 (Apache-2.0) is the safe default and PP-OCR models on ONNX Runtime Web (MIT) are the accuracy upgrade — Scribe.js is AGPL-3.0 and therefore off the table for closed source. Multimodal LLMs are now strong at reading drawing *text* (≈0.9+ on published benchmarks) but weak at *counting symbols* (doors/windows ≈0.2–0.4 exact-match for the best 2025-era models), so automated takeoff must be "LLM proposes, deterministic CV counts, human approves"; a research system that layers CV tools under agents reported 81.6% vs 77.6% for professional estimators on a 10-project benchmark.

### Inferences
- Text-first pipeline: for born-digital sheets `getTextContent()` gives every string with its transform (position, rotation, size) for free and offline — use it for title-block parsing, search and hyperlinking; run OCR only when a page has (almost) no text items or its text is outlined. Many CAD exports use SHX/outlined text, so a per-page "text coverage" heuristic decides.
- Title block extraction: take text items inside the bottom-right / right-edge strip (configurable region template per project, learnt from the first sheet), then (a) sheet number = the largest-font token matching a pattern like `^[A-Z]{1,3}[-.]?\d{1,4}(\.\d{1,2})?[A-Z]?$` or an ISO 19650-style hyphenated ID, (b) title = the multi-word block nearest a "TITLE"/"DRAWING TITLE" label, (c) revision/date/scale by label proximity. Fall back to a cheap LLM call (Haiku-class, structured output) on the cropped title block image + its text for sets that defeat the heuristics; cache the per-project template.
- Auto-hyperlinking: build the set of sheet numbers for the set, then scan all text items for exact matches and for callout patterns (`3/A-501`, `SEE A-201`, detail bubbles where a number sits above a sheet id inside a circle — detectable as two text items within a small circle path from the Q2 geometry). Create link items (internal, and exportable as PDF `/Link` annotations with `/GoTo` destinations). This is deterministic and runs offline; no ML needed for vector sets.
- OCR choice: tesseract.js for general scans (self-host worker, core and `eng.traineddata`; ~10–15 MB cached by the service worker); PP-OCRv5/v6 detection+recognition ONNX models via `onnxruntime-web` when small rotated dimension text matters. Without cross-origin isolation ORT runs single-threaded WASM; try the WebGPU provider first. Enabling threads would require adding COEP (`require-corp` or `credentialless`), which can break cross-origin embeds the whiteboard allows (`frame-src https:`), so treat it as a deliberate trade-off.
- Symbol counting ladder: (1) vector sets — find repeated *vector* instances: hash each small path group (normalised for translation/rotation/scale) and count identical hashes; exact and instant when symbols are blocks; (2) raster template matching (normalised cross-correlation at a few rotations/scales) on a rendered page — implementable in TS/WASM without OpenCV; (3) learned detector via ORT for cluttered sheets; (4) LLM only to *name/classify* the symbol and sanity-check totals, not to count.
- Claude tiling budget (calculation from the documented formula): a full-resolution tile that stays under 4,784 tokens is about 2240×1650 px (80×59 patches = 4,720 tokens). An A1 sheet at 150 DPI is ~4967×3508 px → 3×3 overlapping tiles ≈ 42k tokens, plus one downscaled overview ≈ 4.7k → ~47k input tokens/sheet ≈ US$0.19 on Opus 5.5, US$0.09 on Sonnet 5.5, US$0.005 on Haiku 5.5 (halve with the Batch API). At 300 DPI it is ~36 tiles ≈ 170k tokens ≈ US$0.68 on Opus 5.5 — and exceeds the 20-image threshold, so keep each tile ≤ 3,000 px per side (true here) or split requests. Sending the PDF itself is a poor fit for large-format sheets because page images are capped at the 1,568-token standard tier.
- Prompting pattern that follows the vendor guidance and the benchmark evidence: send overview + extracted text first; give the model a `crop(pageId, bbox, scale)` tool that returns a re-rendered *vector-sharp* tile (cheap for us — it is just another pdf.js render) rather than pre-sending every tile; require structured output with page coordinates; treat returned coordinates as approximate and snap them to vector geometry; never accept counts without a deterministic cross-check.
- MCP design for this stack: one Edge Function exposing board-scoped tools (`list_sheets`, `get_sheet_text`, `render_region`, `list_markups`, `propose_markup`, `propose_measurement`, `set_status`), OAuth via Supabase Auth so RLS enforces board access, and every agent write stored as a *proposal* row (`origin = 'agent'`, `state = 'proposed'`) that a human accepts — mirrors the "pencil until approved" pattern. Rendering in the function is constrained (see Q10), so `render_region` should return a signed URL to a tile rendered by a client or a pre-rendered pyramid rather than rasterising in Deno.
- Privacy: tiles sent to an LLM leave the device — make it opt-in per project, strip title-block personal data where possible, and log each send in the activity log.

### Gaps
- No benchmark covering the *current* (late-2026) model generation on construction drawings was found; AECV-Bench tested Claude Opus 4.5 / GPT-5.2 / Gemini 3 Pro, so today's absolute numbers are unknown.
- DrawingVQA's per-model table could not be retrieved (403), only one figure via a search snippet.

## 8. Revision clouds, callouts, dimension lines and hatches as SVG (and their PDF equivalents)

### Takeaway
All four are a few dozen lines of geometry each in SVG; the PDF side has native homes for them (cloud = Polygon with `/BE /S /C` and `/IT /PolygonCloud`; dimension = Line with `/IT /LineDimension` and leader entries; callout = FreeText with a callout line; hatch = a tiling pattern in the appearance stream). Always export an explicit appearance stream so they look the same everywhere.

### Cited Findings
- PDF cloud border: border-effect dictionary `/S /C` "The border should appear 'cloudy'. The width and dash array specified by BS shall be honored", intensity `/I` 0–2; allowed on square, circle, polygon and (PDF 1.6+) free-text annotations; polygon intent `PolygonCloud` = "intended to function as a cloud" [Inspected] — [PDF 32000-1 Tables 167, 178](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)
- PDF dimension line: Line annotation with `IT /LineDimension`, leader lines `LL` (length), `LLE` (extension), `LLO` (offset), caption `Cap true` with `CP` (caption position) and `CO` (caption offset), endings `LE`, and `Measure` [Inspected] — [PDF 32000-1 Table 175](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)
- CAD convention for cloud direction: Rhino's RevCloud says to "Draw the curve counter-clockwise to make the arc segments bulge away from the center of the cloud", with arc angle "between 90 and 180" controlling the bulge, and options to divide by count or chord length — [Rhino RevCloud](https://docs.mcneel.com/rhino/8/help/en-us/commands/revcloud.htm)
- ezdxf's revision-cloud example builds a closed LWPOLYLINE with a constant bulge of 0.520567050552 per segment (bulge = tan(θ/4), i.e. ≈110° arcs) — [ezdxf example](https://sources.debian.org/src/ezdxf/1.4.1-1/examples/revcloud.py)
- SVG arcs are specified by end points, radii and flags; the SVG implementation notes give the endpoint↔centre conversion needed to turn them into PDF Béziers — [SVG implementation notes](https://www.w3.org/TR/SVG/implnote.html)
- ISO 129-1:2018 ("Technical product documentation — Presentation of dimensions and tolerances — Part 1: General principles") is the current edition and is adopted as BS ISO 129-1:2018; its contents cover dimension lines, extension lines, terminators and placement of values (body text is paywalled) — [iTeh ISO 129-1:2018 sample](https://cdn.standards.iteh.ai/samples/64007/ddfb62a2d7ed4df2a1ac36962279cb2e/ISO-129-1-2018.pdf)
- That Open Components 3.6 ships 2D drafting classes that can be studied for geometry conventions: `LinearAnnotations`, `AngleAnnotations`, `SlopeAnnotations`, `LeaderAnnotations`, `CalloutAnnotations`, `BlockAnnotations`, `DimensionLine`, `TechnicalDrawings`, `DxfExporter` (MIT) [Inspected] — [components index.d.ts](https://cdn.jsdelivr.net/npm/@thatopen/components@3.6.0/dist/index.d.ts); [components-front index.d.ts](https://cdn.jsdelivr.net/npm/@thatopen/components-front@3.6.1/dist/index.d.ts)
- SVG→PDF helpers under permissive licences: `@cantoo/pdf-lib` `page.drawSvg` (shapes, text, transforms, blend modes); `svg2pdf.js` 2.9.0 (MIT, 2026-10-29) with `jspdf` 4.2.1 (MIT); `pdfkit` 0.21.0 (MIT, 2026-11-20) [Inspected/Registry] — [Cantoo README](https://cdn.jsdelivr.net/npm/@cantoo/pdf-lib@2.11.1/README.md); [npm svg2pdf.js](https://www.npmjs.com/package/svg2pdf.js); [npm jspdf](https://www.npmjs.com/package/jspdf); [npm pdfkit](https://www.npmjs.com/package/pdfkit)
- Hand-drawn look, if wanted: `roughjs` 4.6.6 (MIT, last published 2023-11-20) [Registry] — [npm](https://www.npmjs.com/package/roughjs)

### Inferences
- Cloud algorithm: ensure the polygon is counter-clockwise (shoelace sign; reverse if not, so bulges go outward). For each edge of length L choose n = max(1, round(L / s)) scallops for target chord s (tie s to stroke width/zoom-independent paper size, e.g. 6–10 mm on paper), chord c = L / n; emit n arcs `A r r 0 0 sweep x y` with r = c / (2·sin(θ/2)) for a chosen included angle θ (≈110–180°; r = c/2 gives semicircles), sweep flag chosen for outward bulge. Corner handling: start each edge's first scallop at the vertex so arcs meet in a cusp, or pre-inset the polygon by the sagitta so the visual extent matches the picked points. Rectangles/ellipses are the same routine on their perimeter (ellipse: sample by arc length). For PDF export convert each arc to ≤90° cubic Béziers (k = 4/3·tan(φ/4)) inside the `/AP` stream, and set `/BE << /S /C /I 1 >>` + `/IT /PolygonCloud` + `/Vertices` so native tools can re-edit it.
- Dimension line rendering (general drafting practice reflected by ISO 129-1's structure; verify details against the purchased standard): extension lines perpendicular to the measured feature with a small gap at the feature and a short overshoot past the dimension line; thin continuous dimension line; terminators either filled/open arrowheads (mechanical convention) or 45° oblique strokes (architectural convention) — make it a style option; value centred above the line, readable from the bottom or right; units stated once (title/legend) rather than on every value in metric construction drawings. Model as `{p1, p2, offset, terminator, textPos}` so it exports cleanly to `/L`, `/LL`, `/LLE`, `/LLO`, `/LE`, `/Cap`.
- Hatches: SVG `<pattern patternUnits="userSpaceOnUse" patternTransform="rotate(45) scale(k)">` filled into the region path; keep spacing in *paper* units so it is zoom-stable (pattern lives in world space). PDF equivalent: a Type 1 tiling pattern (uncoloured `PaintType 2` lets one definition take any colour) set as the fill colour space inside the annotation appearance stream, or — simplest and most portable — emit clipped hatch line segments explicitly (clip path = region, stroke N parallel lines). A small library of patterns keyed by material (concrete, insulation, earth, brick) with a legend is a takeoff differentiator.
- Callout: FreeText annotation with `/IT /FreeTextCallout`, `/CL` (2- or 3-point leader), `/LE`, `/RD` (inset of text box inside `Rect`); in SVG a `<path>` leader with an optional knee plus a text box item — keep them one board item so they move together.
- Because the app's items are already DOM+SVG in one world layer, one `toPdfOps(item)` function per item type that walks the same normalised path commands used for SVG `d` attributes keeps screen and export in lockstep and avoids rasterising markups.

### Gaps
- The normative text of ISO 129-1:2018 and BS 8888 (terminator sizes, gaps, text heights) is paywalled and was not read; the rendering notes above are general practice, not quoted requirements.
- No source was found documenting how specific PDF viewers synthesise cloud appearance from `/BE` when no `/AP` is present.
- PDF tiling-pattern section references were not extracted verbatim from the spec in this session.

## 10. Real-time review sessions on PDFs

### Takeaway
With one Postgres row per item, a server-ordered **last-write-wins per property** model (the Figma approach) is sufficient and simpler than a CRDT for annotations; add a CRDT only for co-edited rich text inside a comment. Supabase Realtime Broadcast (256 KB payload free / 3 MB paid; 100–2,500 msgs/s by plan) carries ephemeral state, while an append-only Postgres log is the source of truth. Server-side "finish session" PDF generation with pdf-lib fits a Deno Edge Function only for modest files: the hard limits are 256 MB memory, 2 s CPU time and 150 s/400 s wall clock.

### Cited Findings
- Figma's published design: OT was "overkill"; not a true CRDT because "the server is the final authority"; the server tracks the latest value per property per object so "edits to unrelated properties don't conflict"; conflicts resolve to "the last value that was sent to the server"; object creation is explicit with client-generated unique IDs (so offline creation works); child order uses fractional indexing; clients apply edits optimistically and ignore incoming server values that conflict with unacknowledged local edits; on reconnect the client downloads a fresh copy and reapplies offline edits — [Figma engineering blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- Supabase Realtime limits by plan (Free / Pro / Pro no-spend-cap & Team): concurrent connections 200 / 500 / 10,000; messages per second 100 / 500 / 2,500; channels per connection 100; Broadcast payload 256 KB / 3,000 KB / 3,000 KB; Postgres Changes payload 1,024 KB (beyond which only fields ≤ 64 bytes are included); presence messages per second 20 / 50 / 1,000 — [Supabase Realtime limits](https://supabase.com/docs/guides/realtime/limits)
- Supabase Edge Function limits: memory 256 MB; CPU time 2 s per request ("counting only time spent on the CPU, not async I/O"); wall clock 150 s (Free) / 400 s (paid); request idle timeout 150 s (504 after); function size 20 MB (CLI bundle); "The Web Worker API and Node `vm` API are not available"; Node libraries needing multithreading (libvips, sharp) unsupported — [Supabase Edge Function limits](https://supabase.com/docs/guides/functions/limits)
- pdf-lib and its Cantoo fork state they are "Tested in Node, Browser, Deno, and React Native environments" [Inspected] — [Cantoo README](https://cdn.jsdelivr.net/npm/@cantoo/pdf-lib@2.11.1/README.md)
- CRDT libraries (all permissive): `yjs` 13.6.33 — MIT, published 2026-09-23, 28 KB gzip (v14 in beta); `@automerge/automerge` 3.5.0 — MIT, published 2026-09-16, 4.9 MB min / 1.64 MB gzip (WASM inlined); `loro-crdt` 1.19.1 — MIT, published 2026-11-24, JS glue 16 KB gzip plus a 4.2 MB WASM file [Registry/Inspected] — [npm yjs](https://www.npmjs.com/package/yjs); [Bundlephobia yjs](https://bundlephobia.com/package/yjs@13.6.33); [npm @automerge/automerge](https://www.npmjs.com/package/@automerge/automerge); [Bundlephobia automerge](https://bundlephobia.com/package/@automerge/automerge@3.5.0); [npm loro-crdt](https://www.npmjs.com/package/loro-crdt)
- Supabase-specific Yjs glue is not production-grade: `y-supabase` is at `0.0.4-7-alpha`, last published 2023-02-07; `y-indexeddb` 9.0.12 last published 2023-11-02; `y-websocket` 3.1.0 (2026-08-06) needs its own server [Registry] — [npm y-supabase](https://www.npmjs.com/package/y-supabase); [npm y-indexeddb](https://www.npmjs.com/package/y-indexeddb); [npm y-websocket](https://www.npmjs.com/package/y-websocket)
- Precedent: pdf2takeoff runs "live sessions" with a "Yjs CRDT over BroadcastChannel" (same-device tabs) [Vendor/Docs] — [pdf2takeoff](https://github.com/ajflow/pdf2takeoff)
- Fractional-index / patch utilities: `fast-json-patch` 3.1.2 (MIT, 2026-11-21), `jsondiffpatch` 0.7.7 (MIT, 2026-10-29) [Registry] — [npm fast-json-patch](https://www.npmjs.com/package/fast-json-patch); [npm jsondiffpatch](https://www.npmjs.com/package/jsondiffpatch)

### Inferences
- Conflict model for this stack: each item row holds `props jsonb` plus `rev bigint` and `updated_by`. Clients send *property-level patches* (`{id, set: {x, y}, baseRev}`); a Postgres function applies `props = props || patch`, bumps `rev`, and appends to the log in one transaction. Postgres commit order is the "server order", giving LWW per property without clocks. Geometry of one markup is naturally a single property (vertices array) — concurrent edits to the *same* markup's shape by two people are rare and LWW is acceptable; comments/replies are separate rows so they never conflict.
- Ownership rules belong in RLS/trigger, not the client: during a review session a non-owner may *reply* and *set status* on others' markups (new rows) but only the author (or session host) may edit/delete the markup row itself — the same rule Bluebeam-style sessions are known for and one that also removes most conflict cases. Encode as `USING (author_id = auth.uid() OR is_session_admin(board_id))` for UPDATE/DELETE and permit INSERT of reply/status rows to any attendee.
- Channels: Broadcast for cursors, selections, in-progress drags (throttle to ~20–30 Hz, send deltas; payloads are tiny versus the 256 KB limit) and for fan-out of committed patches (lower latency than Postgres Changes and avoids its 1 MB/RLS-per-subscriber cost); Presence for attendee list. On (re)connect, catch up with `select * from item_log where board_id = $1 and seq > $lastSeq` — this is what makes offline-first work: the IndexedDB outbox replays patches with their `baseRev`, and the server rebases them (LWW) or rejects them if the row was deleted or the session is closed.
- Append-only activity log table: `(seq bigserial, board_id, session_id, item_id, actor_id, actor_kind user|agent, op create|update|delete|status|reply|import|export, patch jsonb, prev jsonb, client_ts, server_ts default now())`; revoke UPDATE/DELETE from all roles (and add a trigger that raises), index `(board_id, seq)`; partition by month if large. It doubles as the session "Record" (who did what when), supports undo of one's own operations, and can be exported with the finished PDF. An optional hash chain column (`hash = sha256(prev_hash || row)`) makes tampering evident for contractual reviews.
- When to use a CRDT: only for collaboratively edited long text (comment bodies, notes) — Yjs is the pragmatic choice (28 KB, largest ecosystem) with updates stored as bytea rows and relayed over Broadcast; whole-board CRDT documents fit poorly with one-row-per-item, RLS and server-side queries. Loro's 4.2 MB WASM and Automerge's ~1.6 MB gzip are heavy for a PWA.
- Finishing a session: (1) freeze — set `session.closed_at`, RLS then rejects writes; (2) produce the PDF. Server-side in an Edge Function with `@cantoo/pdf-lib` is feasible for typical sheets (pdf-lib holds the whole document in memory — expect roughly 3–5× file size in heap — so stay well under ~40–50 MB inputs against the 256 MB limit, and under 2 s of CPU: parsing plus appending a few thousand annotation dictionaries is fine; serialising a huge object graph may not be). Use `forIncrementalUpdate` so only the appended annotations are serialised, stream the original from Storage and upload the result via a signed upload URL. For big sets, generate **client-side** in a Web Worker (no limits, works offline) and upload, or fan out one function invocation per file. Rendering/rasterising PDFs in the Edge Function is not realistic (no Web Workers, 2 s CPU).
- Idempotency: key the export on `(session_id, source_file_hash, last_seq)` so retries after a timeout do not duplicate work.

### Gaps
- No published memory/CPU measurements for pdf-lib under Deno on large construction PDFs; the heap multiple above is an estimate to be tested.
- Supabase's limits page does not state request/response body size limits or WASM support in Edge Functions.
- Whether Supabase Broadcast guarantees ordering/delivery across reconnects (it is generally at-most-once) was not confirmed from documentation in this session — the catch-up-from-log design assumes it does not.
- The Supabase docs pages fetched contained embedded text addressed to AI agents (asking them to file a feedback report); it was ignored as unrelated to this research.

- Information container ID is a string of fields separated by a delimiter (hyphen-minus U+002D); the guidance's 7-field example is Project – Originator – (Functional) Breakdown – (Spatial) Location – Form – Discipline – Number, e.g. `123456-ORG-A1-ZZ-MO-A-0001` (older wording: Project – Originator – Volume/System – Level – Type – Discipline – Number) [Inspected] — [UK National Annex guidance (CDBB)](https://www.cdbb.cam.ac.uk/files/national_annex_guidance.pdf)
- Status (suitability) codes: `S0` Work in progress; `S1` Suitable for coordination; `S2` Suitable for information; `S3` Suitable for review and comment; `S4` Suitable for review and authorisation; `S5` Suitable for review and acceptable [sic]; `A1, An` Authorised or accepted (contractual); `B1, Bn` Partial sign-off with comments [Inspected] — [UK National Annex guidance (CDBB)](https://www.cdbb.cam.ac.uk/files/national_annex_guidance.pdf)
- Revisions: preliminary `P01, P02…`, contractual `C01, C02…`; work-in-progress versions add a two-digit suffix after a full stop, e.g. `P01.01`; classification reference: Uniclass 2015 [Inspected] — [UK National Annex guidance (CDBB)](https://www.cdbb.cam.ac.uk/files/national_annex_guidance.pdf)

### Inferences
- Mapping board markups ⇄ BCF: a markup thread (markup + replies + status) = one Topic (`Title` = subject/first line, `Description` = comment, `TopicStatus` = review state, `AssignedTo`, `DueDate`, `Labels` = layer/tags, `CreationAuthor`/dates); each reply = a Comment; the markup's screenshot = viewpoint snapshot. For 2D sheet issues, attach the sheet as a `DocumentReference` and store page number + page-space rectangle in a `ReferenceLink` (deep link back to the board item) — BCF has no native 2D-sheet coordinate, so this part is a convention, while the rest round-trips with any BCF tool.
- 2D ⇄ 3D linking: store `ifcGuids: string[]` on a markup item. In the IFC viewer, pick → `GetGuidFromExpressId` → attach to the active markup; from a markup, `GetExpressIdFromGuid` → highlight/isolate/zoom in three.js. Exported BCF viewpoints then carry `Selection` components by `IfcGuid` plus the camera, so the issue opens on the same elements in Solibri/BIMcollab/Revit-class tools. This is a capability a PDF-only reviewer cannot offer.
- Quantities cross-check: compare a 2D takeoff area/length against IFC quantities (`IfcElementQuantity` via `GetLine` on related property sets, or geometry via `VolumeMeasurement`/`AreaMeasurement`) for the linked elements, flagging discrepancies — a "takeoff vs model" QA feature.
- Section/plan generation from the model (`Clipper` + `ClipEdges`, `TechnicalDrawings`, `EdgeProjector`, `DxfExporter`) could produce a vector 2D view to overlay on the issued PDF sheet using the Q6 alignment — model-vs-drawing comparison.
- ISO 19650 as first-class sheet metadata: parse the container ID fields and `S`/`P`/`C` codes from file names and title blocks (Q7), validate against a per-project convention, show status/revision chips on sheets, and drive revision stacking for Q6 comparisons. Export markup summaries and BCF with these IDs so they slot into a CDE.
- Licences: MIT (That Open) is unrestricted; MPL-2.0 (web-ifc, ifc-lite) is file-level copyleft — using it unmodified in a proprietary bundle is fine, but modifications to MPL-covered files must be published. IDS (Information Delivery Specification) checking via `IDSSpecifications` is another openBIM differentiator.
- The multi-threaded `web-ifc-mt.wasm` needs SharedArrayBuffer and therefore cross-origin isolation, which the current headers do not provide (no COEP); the repo already copies both WASM files to `public/wasm`, so the single-thread build is what actually runs unless COEP is added.

### Gaps
- BCF-API version/endpoint details were not read from the OpenAPI document itself (only repository-level summaries).
- No authoritative changelog of BCF 2.1 → 3.0 was captured.
- That Open's tutorial does not state explicitly that viewpoint component GUIDs are IFC GlobalIds (implied by the BCF schema).
- ISO 19650 itself and the current (2021-revised) UK National Annex are paywalled; the cited CDBB guidance is a template document and the S5 wording looks like a typo in the source — verify against the UK BIM Framework's current guidance.
- Not researched: IFC 4.3 annotation/2D entities, or openCDE Documents API for sheet exchange.

### Inferences
- Where a web app can go beyond a desktop PDF reviewer, drawing the threads together: (1) zero-install, link-shareable, offline-capable PWA sessions; (2) markups that are live board objects *and* standards-compliant PDF annotations, BCF topics and XFDF; (3) 2D-markup ↔ IFC-element linking and model-vs-drawing checks in the same canvas; (4) agent access through an MCP server with human-approval gates; (5) deterministic vector intelligence (snap, auto-hyperlink, vector diff, repeated-symbol count) that runs on-device with no upload; (6) ISO 19650-aware sheet metadata and revision stacks.
- Best reuse strategy for a proprietary product: read pdf2takeoff (Apache-2.0) for an end-to-end reference of the exact feature set on the exact stack (pdf.js + pdf-lib + ORT + Yjs), and EmbedPDF's measurement/annotation plugins (Apache-2.0) for PDF-native measurement semantics; adopt libraries only where they are small and permissive (Flatbush, clipper2-ts, pixelmatch, d3-contour, TanStack, write-excel-file, fast-xml-parser, That Open) and write the thin geometry/CV pieces in-house to stay inside the CSP.
- tldraw's licence change (source-available, production key required) is the notable recent shift; anyone previously treating it as open source should not. Excalidraw remains the MIT reference for whiteboard interaction patterns.
- Any code copied from AGPL repositories (some OpenTakeoff forks, OpenConstructionERP, xeokit) would taint a closed product — study behaviour, do not copy code.
