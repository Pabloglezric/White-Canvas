# Build natively, interoperate through standard PDF

White Canvas should build Bluebeam-class drawing review natively and exchange data with Bluebeam through standard PDF annotations. It should not accept the Bluebeam Developer Terms until the owner has decided how to handle their look-alike clause. Bluebeam works as a PDF-annotation database: every markup is an annotation stored in the PDF with tabular metadata, edited in a Windows-only desktop app (Revu 21.11) and shared through Studio, where Sessions freeze page content and let each attendee edit only their own markups. The browser and phone clients cover about 13 markup types and four basic measurements; takeoff automation, comparison, sets, batch tools, OCR and AI execution stay on Windows. White Canvas today rasterises PDFs to JPEGs of at most 2,400 px, discards the source file, and has no scale, no polyline or polygon items and no per-item metadata. Three foundations therefore gate everything: a retained vector PDF sheet, per-sheet scale with point-list geometry, and cross-type item metadata. The codebase audit's thirteen capabilities sum to roughly **10–29 working weeks for one developer** at base scope, using permissive libraries that fit the current Content-Security-Policy. The blockers are specific: OpenCV.js and `clipper2-wasm` need `'unsafe-eval'`; MuPDF.js, Scribe.js and xeokit are AGPL; and the Developer Terms forbid accessing Bluebeam "in order to build a product using features, functions or graphics similar to" it. The largest open technical question is whether Revu honours a standard `/Measure` dictionary written by another tool; no source has verified it. White Canvas can go beyond Bluebeam on browser, Mac and mobile parity, true co-editing, BCF and IFC linkage, a web-reachable agent server, and infinite-canvas context around sheets.

All facts are as of 25 November 2026. Repository citations are `path:line` at commit `2581a9c`. Size estimates come from the codebase audit and are judgement, not measurement. Nothing in this report is legal advice.

## Bluebeam is a PDF-annotation database edited on Windows

Bluebeam is one per-user annual subscription that bundles three clients around one cloud. Revu 21 is the full editor and runs on Windows only; the current release is **Revu 21.11, dated 1 September 2026** ([Bluebeam release notes](https://support.bluebeam.com/release-notes-all.html)). "Bluebeam on web and mobile" (formerly Bluebeam Cloud) is a browser app plus iOS and Android apps. Studio is the cloud back end, split into Sessions for live co-markup and Projects for simple document management ([Studio FAQs](https://support.bluebeam.com/studio/resources/studio-faqs.html)). UK prices per user per year, VAT-inclusive, are **Basics £264, Core £330, Complete £438 and Max £588**; the Max price is introductory and holds only until renewal in 2027 ([Bluebeam UK pricing](https://www.bluebeam.com/uk/pricing/)). Only Core and above can create or manage Sessions and Projects. Anyone with a free Bluebeam ID can join them, which is why Studio spreads between firms ([Subscription features](https://support.bluebeam.com/revu/subscription/subscription-features.html)).

The unit of work is the PDF file. Markups "are part of the PDF, but not part of the underlying content" ([Create and edit markups](https://support.bluebeam.com/user-manual/menus/tools/create-edit-markups.html)). A PDF produced by Revu stores a line markup as an ordinary annotation object (`/Type/Annot /Subtype/Line`) with private extra keys such as `/BSIColumnData` for custom-column values ([pypdf discussion #2270](https://github.com/py-pdf/pypdf/discussions/2270)). Every markup is also a row in the Markups List, a live table with built-in columns, six kinds of custom column including formulas, status models with per-markup history, threaded replies, and filters that dim non-matching markups on the drawing ([Markups List](https://support.bluebeam.com/user-manual/menus/window/markups-list.html); [Custom columns](https://support.bluebeam.com/user-manual/menus/window/custom-columns.html); [Filters](https://support.bluebeam.com/user-manual/menus/window/markups-list-filter.html)). Reusable configuration travels as small sidecar files: `.btx` tool sets, `.bax` exported markups and `.bex` Sets. The lesson for White Canvas is direct. Interoperate at the PDF level, not at any Bluebeam cloud format.

Studio avoids concurrency problems; it does not solve them. A Session accepts PDFs only, up to **500 attendees, 5,000 files, 1 GB per file and 10 MB per markup** ([Studio FAQs](https://support.bluebeam.com/studio/resources/studio-faqs.html)). Attendees can "change, edit, and delete markups and measures that you have created" and reply to others, but cannot edit others' markups, and tools that change PDF content are unavailable ([Attend a Studio Session](https://support.bluebeam.com/user-manual/menus/window/attend-studio-session.html)). Studio "keeps a complete record of all activity in the Session", and the host finishes by choosing whose markups are written back into the saved PDFs ([Studio Sessions guide](https://support.bluebeam.com/studio/how-to/studio-sessions-guide-for-revu.html)). Bluebeam's own guidance treats more than 100 sheets, more than 250 MB or more than 20 active markers as large ([Best practices for Studio](https://support.bluebeam.com/studio/how-to/best-practices.html)). Projects use exclusive check-out. Data sits in six isolated regions; the UK region is on AWS in London, and each region needs a separate Bluebeam ID ([Bluebeam Studio regions](https://support.bluebeam.com/studio/resources/changing-studio-region.html)).

Bluebeam's AI is desktop-bound. Max ships a local MCP server inside Revu 21.9 or later that lets Claude, GitHub Copilot CLI, ChatGPT and AnythingLLM read and edit markups in the active PDF, and Bluebeam states that it "can be used only with the desktop version of Revu" ([Revu and MCP](https://support.bluebeam.com/revu/resources/revu-mcp.html)). Smart Review and Smart Overlay are still in preview. Smart Review supports imperial measurements only, and Smart Overlay has no alignment step ([Smart Overlay and Smart Review FAQs](https://support.bluebeam.com/revu/resources/smart-overlay-review-faq.html)). No first-party automatic takeoff exists; Bluebeam's 2026 guide says "the estimator defines what to look for, reviews the results, and validates what gets counted" ([Construction takeoffs guide 2026](https://www.bluebeam.com/resources/construction-takeoffs-guide-2026/)).

Reviewers name the same few things as valuable: live Sessions with a log, shareable tool sets, scale-accurate takeoff with automatic totals, the Markups List as a tracking database, and revision comparison ([Software Advice reviews](https://www.softwareadvice.com/cms/bluebeam-revu-profile/reviews/)). Complaints cluster where a web app competes. Revu "is not supported on Apple Mac devices" ([Ways to use Bluebeam on macOS](https://support.bluebeam.com/bluebeam-cloud/how-to/use-bluebeam-macos.html)). A third-party compilation put the iOS app at **1.51 across 369 App Store ratings** on 7 August 2026 ([Fervor Studio review](https://fervorstudio.ca/news/bluebeam-revu-review-pricing-alternatives/)). Browser Sessions have no offline access ([Bluebeam app and browser comparison](https://support.bluebeam.com/bluebeam-cloud/features/bluebeam-cloud-app-and-browser-comparison.html)).

### Where the notes disagree or could not verify

**Plan tier for scripting.** Bluebeam contradicts itself. The UK pricing page lists "Scripting commands for custom automations" under Complete ([Bluebeam UK pricing](https://www.bluebeam.com/uk/pricing/)). The Scripts manual page says Complete or Max ([Scripts](https://support.bluebeam.com/user-manual/menus/document/use-scripts.html)). The plan matrix ticks "Implement scripting commands" for Max only ([Subscription features](https://support.bluebeam.com/revu/subscription/subscription-features.html)). This report does not pick one. Redaction and form authoring show the same pattern: the manual pages say Complete and Max, and the matrix ticks all four plans.

**Fate of the Bluebeam Cloud field tools.** One notes file treats the punch, RFI and submittal tools as removed in August 2024. The other found no official retirement notice and marks the date and mechanics as unverified. The evidence is a community thread in which users reported Cloud Projects being "eliminated August 27th" and a Bluebeam product manager confirmed "the gap created by removing the Cloud functionality before the replacement is ready" ([Bluebeam Community thread](https://community.bluebeam.com/discussion/600/leave-bluebeam-cloud-alone)). The removal is therefore confirmed by staff on a forum; the exact date is user-reported. Today Bluebeam describes RFIs as a Markups List workflow ([Construction RFI Software](https://www.bluebeam.com/workflows/rfis/)).

**Other open points.** The regions page lists "Bluebeam on web and mobile" only under US and CA, while the status page lists a web component under DE and the UK trial form offers a UK server ([Bluebeam Studio regions](https://support.bluebeam.com/studio/resources/changing-studio-region.html); [Bluebeam status history](https://status.bluebeam.com/history); [Bluebeam UK trials](https://www.bluebeam.com/uk/trials/)). The plan matrix advertises set comparison "with automatic alignment" for Max, while the FAQ says Smart Overlay has none. The UK trial page says 14 days; one notes file records a 15-day Max trial. A pricing-page footnote says mobile measurement is "not yet available on Android", while the Android 1.21 notes of 18 November 2026 add it. The `.bpx` profile extension is confirmed by community sources and a Bluebeam community article, not by a support page read in this research. One notes file could not re-confirm the own-markups-only Session rule from a 2026 source; the other read it on the current "Attend a Studio Session" manual page, so this report treats it as confirmed.

## Track A: exchange PDFs freely; the Studio API needs a contract decision first

### Standard PDF annotations are the dependable bridge

Standard ISO 32000 annotations are the write path into Revu. Revu serialises its own markups as standard annotation objects. Its import "takes the markups from a PDF, XML, or [BAX] file", and "FDF files containing annotations generated from other PDF applications may also be imported" ([Markups List, Revu 21 help](https://support.bluebeam.com/online-help/revu21/Content/RevuHelp/Menus/Window/Panels/Markups/Markups-List--MTV.htm)). One open-source takeoff tool already writes "standard Line, PolyLine, Polygon and FreeText annotations via pdf-lib, with the measurement in the comment" and advertises that they open in Bluebeam, a self-reported claim ([pdf2takeoff](https://github.com/ajflow/pdf2takeoff)). No systematic test of which third-party annotation types Revu preserves on open, edit and save was found, so the roadmap starts with one. The standard gives native homes to the construction primitives: a cloud is a Polygon with border effect `/BE /S /C` and intent `/IT /PolygonCloud`; a dimension is a Line with `/IT /LineDimension`; a callout is a FreeText with `/IT /FreeTextCallout` and a `/CL` leader; review status is a reply Text annotation carrying `/State` and `/StateModel /Review` ([ISO 32000-1](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)). The recommended mapping is author to `/T`, subject to `/Subj`, comment to `/Contents`, item id to `/NM`, layer to optional content, and always an explicit appearance stream so every viewer draws the same thing. Bluebeam-only data does not travel: custom columns live in the private `/BSIColumnData` key, which the pypdf maintainer could not find in the PDF 1.7 or 2.0 references ([pypdf discussion #2270](https://github.com/py-pdf/pypdf/discussions/2270)).

**Measurements are the unverified part.** ISO 32000-1 defines a `/Measure` dictionary on Line, PolyLine and Polygon annotations and page `/VP` viewports for scale ([ISO 32000-1](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)). Whether Revu reads a `/Measure` written by another tool, recalculates from it, or needs its own private keys is not established. Two independent projects write the standard form for Bluebeam users, and both say they have not checked the result in Revu; one states "Bluebeam publishes no dictionary documentation for its measurement markups" ([planyr pull request #2448](https://github.com/mikeab7/planyr/pull/2448); [openrevu fork issue #12](https://github.com/mdouglass95/openrevu/issues/12)). The sources also disagree on which ISO edition puts `/Measure` on an annotation; the ISO 32000-1 text is the better authority. The safe design writes the scale twice (page `/VP` and per-annotation `/Measure`), puts the measured value in `/Contents` and in the appearance stream, and expects that a Revu user may need to re-apply scale. Closing the question needs a hands-on test in a licensed copy of Revu.

Bluebeam's side formats are a weaker bridge. A `.btx` tool set is XML whose payload is a zlib-compressed, hex-encoded PDF annotation dictionary, and the community decoder's author had "only decoded about half" of it ([UChapter2 decoder thread](https://uchapter2.com/brainery/tips-tricks/forum/topic/tool-for-decoding-bluebeam-configuration-and-markup-files/)). Generation is feasible, and Bluebeam itself hosts a Claude skill that builds `.btx` files ([Tool Set, Profile and Custom Columns Builder](https://community.bluebeam.com/kb/articles/358-tool-set-profile-custom-columns-builder)). The format is undocumented and version-dependent, so treat `.btx` import as a later, optional switching aid.

### The Studio API reads markups but cannot write them

One public REST API exists: the Bluebeam Studio API, version 1.0.0, with a UK host at `https://api.bluebeamstudio.co.uk` ([Developer Portal API docs](https://developers.bluebeam.com/docs); [Get started in the Developer Portal](https://support.bluebeam.com/developer/getting-started-dev-portal.html)). Portal access needs an active Core, Complete or Max plan, so the entry cost is one Core seat at £330. Authentication is OAuth 2.0 authorization code plus refresh token with a client secret. Access tokens last 60 minutes, and refresh tokens rotate on every use and expire if unused for 7 days ([Authentication Guide](https://support.bluebeam.com/developer/authentication-guide.html)). A browser SPA cannot hold that secret, so the integration would live in a Supabase Edge Function that exchanges codes, stores rotating tokens and proxies calls. New apps start in a Sandbox where "only the account that owns the application can authenticate"; production needs written approval, with a status update "within 5 business days" ([Get started in the Developer Portal](https://support.bluebeam.com/developer/getting-started-dev-portal.html)). Numeric rate limits are not published on any page readable without login. Bluebeam's own guide is inconsistent on scope names: its example request uses `full_prime` and its example response shows `full_user`.

The API supports a full PDF round trip and read-only markup data. The documented sequence is: create a Session, register a file, `PUT` the PDF to an upload URL that is valid for 10 minutes, confirm, invite reviewers, set the Session to `Finalizing`, request a snapshot and download the combined PDF ([Studio Session Guide](https://support.bluebeam.com/developer/studio-session-guide.html)). Sessions do not accept PDF/A files. While a Session is open, `GET /publicapi/v2/sessions/{sessionId}/files/{fileId}/markups` and `.../markups/details` return markups as JSON, the latter with roughly 90 properties including `vertices`, `path`, colours and `measure`. A `PUT` changes status. The OpenAPI document contains no operation that creates, edits or deletes a markup ([Developer Portal API docs](https://developers.bluebeam.com/docs)). Webhooks fire on Session and document events only, so near-real-time markup mirroring means polling against unpublished limits ([Webhooks](https://support.bluebeam.com/integrations/use-webhooks.html)).

Nothing else is reachable from a hosted web app. No embeddable viewer or JavaScript SDK was found, and Bluebeam's Acceptable Use Policy lists "frame" among prohibited acts ([General Terms and Conditions of Use](https://www.bluebeam.com/legal/terms-of-use/)). The `studio://` link opens a Session but cannot target a document or page ([Bluebeam Community discussion 6613](https://community.bluebeam.com/discussion/6613/feature-request-deep-linking-into-studio-open-to-specific-document-page-via-studio-url)). The Max MCP server is local to Windows Revu, so White Canvas cannot call it server-to-server; the two could only meet inside a user's own desktop agent connected to both.

### The Developer Terms make API access a decision, not a default

**This is a factual summary of published terms and public records. It is not legal advice; a qualified IP and commercial lawyer should review it before the owner relies on it.**

Accepting the Bluebeam Developer Terms of Use (last updated May 2026) is required to get API credentials. Section 8 says a developer shall not "(c) reverse engineer or access the Bluebeam Technology in order to build a product using features, functions or graphics similar to the Bluebeam Technology; (d) copy any features, functions or graphics of the Bluebeam Technology", nor "(j) use the API in any of Your Integrations to replicate or attempt to replace the user experience of the Company Offering" ([Developer Portal](https://developers.bluebeam.com/)). "Bluebeam Technology" is defined to include the desktop, mobile and SaaS software, not only the API. Bluebeam controls production approval and "may deny those requests, or revoke access". The same Terms forbid using end-user data to train or benchmark any AI model. They are governed by California law with JAMS arbitration in Los Angeles, even for a UK developer. The risk is plain: a product that signs up for API access and also ships markup, measurement, tool-library and session features that resemble Bluebeam's sits in the zone these clauses address.

The ordinary customer terms carry a second, smaller exposure. The General Terms bar a user from acting to "reverse engineer, decompile, disassemble, or attempt to derive the source code or underlying ideas of the Services or Software" ([General Terms and Conditions of Use](https://www.bluebeam.com/legal/terms-of-use/)). The clause opens with a carve-out, "Except as permitted by open-source terms, applicable law, or these Terms", and interoperability exceptions vary by jurisdiction. For a UK customer the terms are under English law with London arbitration. Any hands-on testing in Revu, including the `/Measure` test above, means accepting these terms. Decoding `.btx` or `.bax` files inside a licensed copy is closer to that clause than opening White Canvas's own exported PDF to see how it displays; counsel should confirm where the line sits.

The owner must choose between three positions. **Option 1, file-only interoperability:** never accept the Developer Terms, build natively, and exchange standard PDFs, FDF and CSV. This keeps the roadmap free of clause 8 and costs the Session round trip. **Option 2, declared partner:** talk to `integrations@bluebeam.com` before signing up and position White Canvas as a complement that pushes sheets to Sessions and pulls markups back, as Vectorworks and Graphisoft do ([Vectorworks newsroom](https://www.vectorworks.net/en-US/newsroom/bluebeam-integration); [Graphisoft listing](https://integrations.bluebeam.com/apps/bluebeam-studio-connection/)). This buys reach into Bluebeam's installed base and accepts Bluebeam's approval power. **Option 3, do both without clearance:** sign up, integrate, and ship look-alike features. This is the position the clauses conflict with. This report recommends Option 1 now, and Option 2 only after legal advice.

Trademark and patent exposure is secondary but real. Registered US marks include BLUEBEAM, REVU, BLUEBEAM REVU, BATCH LINK and STUDIO, the last for "computer server software to provide hosting of multiple collaborative users" ([USPTO record](https://tmsearch.uspto.gov/search/search-results/85607989)). "Tool Chest" has no live Bluebeam US registration, though Bluebeam has long claimed it with a ™ symbol ([USPTO search](https://tmsearch.uspto.gov/search/search-results?q=tool%20chest)). UK and EU registers were not searched. Bluebeam is assignee of **46 granted US patents in 26 families** covering document comparison and alignment, palette-style saved tools, sequenced annotations, dynamic fill, legends with cumulative quantities, sets, batch link generation, visual search, session recording, cross-device markup synchronisation and 2D–3D linkage ([USPTO Patent Public Search](https://ppubs.uspto.gov/pubwebapp/external.html?q=%28Bluebeam%29.as.&db=USPAT)). Only titles and ten abstracts were read; claims, expiry and UK validation were not checked. Several roadmap items below overlap these themes, so a freedom-to-operate review belongs before the flood-fill, live-legend, auto-numbering and auto-hyperlink features ship.

The project's own rule points the same way. `PROJECT_BRAIN.md:30` records "Own visual identity; no reference-product branding or assets." That line was written about the whiteboard reference product; applying it to Bluebeam is a reasonable reading, not an explicit one. In practice: original icons, original layout, no Bluebeam stock tool sets, hatches or stamp artwork, and neutral feature names such as "tool presets" and "review session".

## Track B: thirteen capabilities rest on three missing foundations

### White Canvas today is a solid whiteboard with a raster PDF

The engine is sound for this work. A board is a flat map of 15 item types, each one `board_items` row with `data` jsonb and a server-arbitrated `rev` (`src/board/types.ts:3-5`, `supabase/migrations/0001_init.sql:59-68`). Live editing, presence, four roles under RLS, an offline outbox, per-item SVG export and a nine-tool agent server already exist (`src/board/sync.ts:392-454`, `supabase/functions/mcp/index.ts:211-471`). New item types need no migration.

The PDF path is the weak point. `importPdf` rasterises the first 40 pages to JPEG with the long side capped at 2,400 px and does not upload the original file (`src/board/importers.ts:128-145`, `:190-193`). By the audit's arithmetic an A1 sheet lands at about 72 dpi and an A0 at about 51 dpi. No text layer, page label or annotation survives. Existing boards cannot be upgraded later, because the source was never stored. Export to PDF is the browser print dialog (`src/board/export.ts:267-287`).

Three foundations are missing, and they gate most of the list. **Foundation A** is a retained, vector-rendered PDF sheet item with a text layer. **Foundation B** is per-sheet scale plus point-list geometry: no unit or calibration exists anywhere in `src/`, items are boxes or two-ended connectors, and PDF pages sit at an undocumented 1.2 world units per point (`src/board/importers.ts:150`). **Foundation C** is cross-type metadata: layer, status, subject, timestamps and custom fields. Two structural costs apply to all of it. First, `normalizeItem` is a strict whitelist, so any new field that is not added to `src/board/validate.ts` disappears after the first reload. Second, every new item type pays for three renderers (DOM/SVG, the overview canvas, export) plus validation and the agent schema. The audit's advice is to consolidate the construction items onto one generic point-list annotation type. Whole-item last-write-wins is the other structural risk: two reviewers changing different fields of one item at commit time produce one winner for the whole item (`src/board/sync.ts:259-300`).

**Stay on pdf.js for the underlay.** Version 6.5.438 ships the pieces a deep-zoom sheet needs: `getViewport` with offsets for tile rendering, `recordOperations` with an `operationsFilter` to skip drawing operations outside a tile, and a separate renderer worker enabled through `GlobalWorkerOptions.rendererSrc` ([pdf.js api.d.ts](https://cdn.jsdelivr.net/npm/pdfjs-dist@6.5.438/types/src/display/api.d.ts)). A scan of its bundles found no `eval` or `new Function`, so the current policy already permits it. The design is a low-resolution whole-page bitmap plus a pool of tiles rendered at zoom times device-pixel ratio. Safari rejects any canvas over 16,777,216 px ([PQINA](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/)), and pdf.js itself drops to 5,242,880 px on iOS and Android ([pdf_viewer.mjs](https://cdn.jsdelivr.net/npm/pdfjs-dist@6.5.438/web/pdf_viewer.mjs)). The renderer worker has not been verified on iOS Safari.

**Scale is one factor per viewport.** PDF space is 1/72 inch times `UserUnit`, so a ratio scale gives `metresPerPoint = (0.0254 / 72) × UserUnit × scaleDenominator`, which is 0.035278 m per point at 1:100. Two-point calibration gives `knownLength / hypot(Δx, Δy)`. Store geometry in PDF points and convert at display time. Mirror the standard's viewport rule, where a measurement uses the viewport of its first point, so export stays lossless ([ISO 32000-1 §12.9](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)). Snap-to-content comes from `getOperatorList()`: pdf.js 6.5.438 emits each path as an `OPS.constructPath` operation with a `Float32Array` of draw commands and a bounding box ([pdf.worker.mjs](https://cdn.jsdelivr.net/npm/pdfjs-dist@6.5.438/build/pdf.worker.mjs)). That layout is internal and has changed across majors, so pin `pdfjs-dist` exactly and add a fixture test. Flatbush indexes 1,000,000 rectangles in 109 ms on its published benchmark ([Flatbush README](https://cdn.jsdelivr.net/npm/flatbush@4.8.0/README.md)).

**Write annotations through the low-level API.** No permissive JavaScript library offers a turnkey markup writer. `@cantoo/pdf-lib` 2.11.1 is the maintained MIT fork, runs in the browser and Deno, has no `eval`, and exposes `context.obj`, `context.formXObject`, `context.register` and `page.node.addAnnot`, plus incremental save ([PDFContext.d.ts](https://cdn.jsdelivr.net/npm/@cantoo/pdf-lib@2.11.1/es/core/PDFContext.d.ts)). The original `pdf-lib` 1.17.1 was last published on 6 November 2021. Generate each appearance stream from the same path data `src/board/export.ts` already uses for SVG. For import, pdf.js `getAnnotations()` returns geometry, author, replies and review state, but its worker reads neither `/Measure` nor `/BE`; recover those from the raw dictionaries with pdf-lib. The end-to-end write has not been tested in other viewers.

**Sessions need per-property merge and an append-only log, not a CRDT.** Figma's published design keeps the server as final authority and resolves conflicts per property per object ([Figma engineering blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). For White Canvas that means property-level patches applied in a Postgres function, an own-markup rule in RLS keyed on `data->>'by'`, server-set authorship for all item types (today only commenter comments, `supabase/migrations/0002_hardening.sql:77-79`), and a `board_events` table with update and delete revoked. Copy Bluebeam's two-timestamp idea: offline markups enter the Record at upload time while the markup keeps its real creation time ([Work offline in Studio](https://support.bluebeam.com/studio/how-to/work-offline.html)). The close-out PDF should be generated client-side in a worker for large sets, because a Supabase Edge Function is limited to **256 MB memory and 2 s CPU time** ([Supabase Edge Function limits](https://supabase.com/docs/guides/functions/limits)).

Platform limits matter as much as licences. Supabase Realtime Broadcast payloads are capped at 256 KB on the free plan and 3,000 KB on paid plans ([Supabase Realtime limits](https://supabase.com/docs/guides/realtime/limits)). Per-item data is capped at 1 MB and `boards.settings` at 16 KB (`supabase/migrations/0002_hardening.sql:11-23`), so OCR word positions belong in a side asset and large preset libraries need their own table. The storage bucket caps files at 50 MB (`supabase/migrations/0001_init.sql:267-268`); a Bluebeam Session accepts 1 GB per file. Stored files are not cached by the service worker (`public/sw.js:53`), so an offline sheet workflow needs its own file cache. Device-only boards have no server, roles or bucket, so every feature must work there or be disabled explicitly.

## Track C: White Canvas goes beyond where Bluebeam is structurally absent

**Platform parity is the first opening.** Bluebeam's full editor is Windows-only. The web client shows stamps without letting users select or edit them, cannot move or resize measurement markups brought from Revu, documents no custom-column authoring, and has no offline mode ([Markup compatibility in Bluebeam on web](https://support.bluebeam.com/bluebeam-cloud/resources/markup-compatibility.html)). White Canvas is one codebase for every browser, with an offline outbox and Playwright projects for desktop and two foldable touch viewports (`playwright.config.ts:3-20`). Every capability in the table above ships to web, Mac and mobile at once. The caveat is honest: real-device checks on foldables, iOS Safari and stylus pressure are not done (`docs/AUDIT.md:102-117`).

**True co-editing is the second.** Studio gives each markup one owner and freezes the page set, so two people never edit the same object. White Canvas already merges live edits from many people on the same items. It can offer Bluebeam's single-owner rule as an optional session mode and keep open co-editing as the default, including page changes during a live review. First-class snag and RFI objects are the related gap: Bluebeam removed its dedicated field modules and now treats them as markups plus custom columns, while White Canvas already has a `card` item with status, assignee, due date and tags (`src/board/types.ts:147-156`).

**Open standards are the third.** No native BCF import or export was found in Bluebeam's 3D PDF page, API specification or integrations directory; where BCF appears, the partner application produces it ([Vectorworks newsroom](https://www.vectorworks.net/en-US/newsroom/bluebeam-integration)). That absence is inferred, not stated by Bluebeam. A BCF 3.0 topic carries title, status, assignee, due date, labels, comments and viewpoints that address model elements by IFC GUID ([BCF-XML 3.0 documentation](https://github.com/buildingSMART/BCF-XML/tree/release_3_0/Documentation)). White Canvas already loads IFC through `web-ifc`, whose API includes `GetGuidFromExpressId` and `GetExpressIdFromGuid` ([web-ifc-api.d.ts](https://cdn.jsdelivr.net/npm/web-ifc@0.0.81/web-ifc-api.d.ts)). Storing `ifcGuids` on a markup links a 2D cloud to model elements in the same canvas, and [`@thatopen/components` 3.6.0](https://www.npmjs.com/package/@thatopen/components) (MIT) implements BCF export and import of BCF 2.1 and 3.0 files on three.js and web-ifc ([That Open BCFTopics tutorial](https://docs.thatopen.com/Tutorials/Components/Core/BCFTopics)). BCF has no native 2D-sheet coordinate, so the page rectangle travels as a convention in a reference link. Bluebeam holds US patents on linking 2D documents to 3D models (11,468,208 and 12,045,544) and on annotations tied to a 3D view (8,823,744) ([USPTO Patent Public Search](https://ppubs.uspto.gov/pubwebapp/external.html?q=%28Bluebeam%29.as.&db=USPAT)); the claims were not read, and this feature needs a freedom-to-operate check. XFDF (ISO 19444-1) and ISO 19650 metadata complete the set: container IDs such as `123456-ORG-A1-ZZ-MO-A-0001`, suitability codes `S0`–`S5` and revisions `P01`/`C01` can be parsed from file names and title blocks ([UK National Annex guidance](https://www.cdbb.cam.ac.uk/files/national_annex_guidance.pdf)). No Bluebeam statement on ISO 19650 was found.

**A web-reachable agent server is the fourth.** Bluebeam's MCP server needs Windows, Revu 21.9 or later and the Max plan. White Canvas already exposes nine tools over Streamable HTTP from a Supabase Edge Function with hashed tokens and rate limits. Today an agent cannot see a drawing: `describe` hides `asset:` sources and no tool returns page text or a rendered region (`supabase/functions/mcp/index.ts:103-127`). Adding sheet text, a region render and proposal-style writes changes that. The evidence says how far to trust the model. On AECV-Bench the best 2025-era models read drawing text well but scored 0.39, 0.28 and 0.16 exact-match on door counting ([AECV-Bench](https://arxiv.org/abs/2601.04819)). A layered system of computer-vision tools under agents scored 81.6% against 77.6% for professional estimators in a vendor-authored paper ([Handoff-H1](https://arxiv.org/abs/2608.15032)). The design rule follows: the model proposes, deterministic geometry counts, a person approves. Store agent writes as proposals, as the open takeoff tools do ("Agent work is marked as pencil proposals until a person accepts it", [OpenTakeoff](https://github.com/kleenkanteen/opentakeoff)). Sending tiles to a model must be opt-in per project and logged.

**Infinite-canvas context is the fifth, and it is White Canvas's own.** Bluebeam's unit of work is a PDF file; its Max-only Stitching feature exists to join sheets into one continuous view. On a board, sheets from several files sit side by side with the IFC model, the snag cards, tables, notes and embeds around them, and a compare or legend item is one more object on the same surface. This is an inference from the two products' data models, not a sourced comparison. Deterministic on-device vector work adds to it: a path-hash diff between revisions, repeated-symbol counts from identical vector groups, and sheet-number hyperlinks from the text layer all run without an upload. Metric and UK fit is concrete too: Bluebeam's FAQ answers "Does Smart Review support metric measurements? No." ([Smart Overlay and Smart Review FAQs](https://support.bluebeam.com/revu/resources/smart-overlay-review-faq.html)).

Do not try to beat desktop Revu's depth in takeoff automation, batch document control and PDF fidelity. Interoperate with those through the PDF.

## Five phases order the work by dependency

The audit's dependency order is capability 6 and capability 1 first, then 2, then 3, 5, 8 and 10, then 7, 9 and 11, with 12 and 13 growing alongside once 1 and 2 exist. The phases below follow it. Base sizes sum to 8 L and 5 M. By this report's arithmetic on the audit's size key (8 × 1–3 weeks plus 5 × 2–5 days) that is the 10–29 working weeks quoted at the top; every "XL" extension is on top, and the audit built no prototype.

Phase 0 is cheap and removes the two largest unknowns. The Revu test decides how much of capability 11 is worth building: if Revu ignores a third-party `/Measure`, measurements export as correct-looking annotations with the value in the comment, and scale is re-applied in Revu. That test needs a Revu licence, which means accepting Bluebeam's General Terms; the 14-day trial is the low-cost route. The item-model decision matters as much. One generic annotation item pays the three-renderer cost once for clouds, polylines, polygons, dimensions and counts, and field-level merge must land before review sessions, or concurrent status edits will be lost.

Phase 1 changes the import contract. Uploading the original PDF needs the bucket limit reviewed against real drawing sets, a new entry in `fileRefs` and `adoptAssets` so pasted boards do not point at another board's folder (`src/board/assets.ts:129-160`), and a decision on the 1.2 units-per-point placement, which differs from the 96-per-inch implied by the A-series frame presets. Existing boards keep their JPEG pages and need a re-import path.

Three risks run across the plan. The Supabase free plan pauses after a week of inactivity and has no point-in-time recovery (`docs/AUDIT.md:102-117`), which is not acceptable for a contractual review trail, so the activity log needs a paid plan before review sessions are sold as a record. The 228 KB initial transfer depends on heavy chunks staying lazy and out of the precache (`vite.config.ts:7-35`), so every new engine must match that rule. And no benchmark compares pdf.js 6.x with PDFium-WASM on dense CAD sheets, so the PDFium fallback (about 4.65 MB of WASM) stays in reserve until real drawings are profiled.

## Conclusion

The research changes the framing of "integrate". Bluebeam's moat is not a cloud format or an API; it is the PDF annotation plus the accumulated assets around it: tool sets, custom columns, statuses and hyperlinked sets. White Canvas does not need Bluebeam's permission to read and write that PDF, and it loses freedom the moment it signs terms that restrict building similar features. The useful integration is therefore the humble one: take a Bluebeam-marked PDF in with its authors, replies and statuses intact, and hand back a PDF that lists cleanly in Revu.

The second shift is where the product should be measured. Matching Revu feature for feature on Windows is a losing brief. A reviewer on a Mac, a site manager on a phone and an agent on the web each get a reduced Bluebeam today. If the three foundations land first, White Canvas gives all of them the same sheet, the same measurements and the same issue list on one surface, with the model beside the drawing. One licensed afternoon in Revu, testing what it does with a standard `/Measure`, will say how much of that surface can also be handed back to Bluebeam users.
